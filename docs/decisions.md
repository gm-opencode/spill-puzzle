| 9 | 2026-11-20 | Grid (spec §3): all 9 candidates (`cols ± 1` × `rows ± 1`) are clamped to ≥ 2; ties keep the first candidate in the order `cols-1..cols+1`, then `rows-1..rows+1` | The spec doesn't say whether ±1 may go below 2, or how to break ties | Deterministic. Note the spec formula picks 3×3 = 9 for a square image at N = 12 (score 0.25 vs 0.29 for 3×4). The UI must show the actual count (FR-2.2) |
| 10 | 2026-11-20 | Edge curve (spec §4.1–4.2) concretised as generator version 1: RNG draws per edge in the order `dir, center, size, neck, j1, j2`; all horizontal edges row-major, then all vertical edges row-major. `dir = +1` puts the tab on the left-hand side of the canonical direction (horizontal edges left→right, so up; vertical edges top→bottom, so right). Bulb radius = `0.55·size`, with the bulb's centre at height `size − r` so the peak is exactly at `size`. Six cubics: shoulder, neck-in (starts inwards so the neck pinches), two quarter-arc bulb cubics, neck-out, shoulder. `j1`/`j2` offset the neck base ends, as written in the spec | The spec gives only the outline of the curve | All control points stay within `u ∈ [0, 1]`, `|v| ≤ size ≤ 0.24`, which is inside the `0.28` pad, so outlines are guaranteed to stay within piece bounds. **Any change here requires bumping `GENERATOR_VERSION`** (snapshot tests will fail otherwise) |
| 11 | 2026-11-20 | Reversed edges are produced by reversing the forward Bézier segments, not by recomputing them, and the first/last points are set to the exact corner coordinates | Floating-point recomputation in the opposite direction could differ in the last bit | Neighbouring pieces share bit-identical edge points (tested) |
| 12 | 2026-11-20 | Dev-only debug page at `#/debug/shapes` lives in `src/debug/` and is loaded behind `import.meta.env.DEV` | Not in architecture §2. It is development tooling, not product UI | It is removed from production builds (verified: no debug code in `dist/`) |
| 13 | 2026-11-20 | Milestone 0 completed after Milestone 1 (closes the gap in #5): Playwright with Chromium desktop, Pixel 7 and WebKit iPhone 15 projects, GitHub Actions CI (format check → lint → typecheck → unit → build, then e2e), and `export {}` placeholder modules with `TODO(Mx)` comments for the rest of architecture §2. | 14 | 2026-11-20 | Bevel stroke offsets are the reverse of spec §5 step 3: the light stroke is offset by (+1, +1) and the dark one by (−1, −1) | Strokes are clipped to the piece, so only the half of the stroke that shifts *into* the shape shows. With the spec's offsets the highlight would appear on the bottom-right inner edge (lit from below). Swapping gives the usual top-left light | Pieces look raised, lit from the top-left. Constants are in `BEVEL` in `bakePieces.ts` |
| 15 | 2026-11-20 | Pieces are drawn straight into the atlas at their packed frame (translate + clip), instead of into a per-piece canvas that is then copied. The shared drawing code lives in a new `src/game/bake/bakePieces.ts`, used by both the worker and the main-thread fallback | Same output as spec §5 steps 1–5 with one canvas per atlas instead of one per piece. Keeps a single code path for both modes | `bake/` has one file more than architecture §2. Frames are `ceil(bounds)` px with a 2 px transparent gap between them. A frame's top-left maps to the piece bounds' world origin (`worldX`, `worldY`) |
| 16 | 2026-11-20 | Atlas packing: tallest first, shelves of a width that makes one atlas roughly square (rounded up to 64 px, capped at the max size). Atlas sizes are not powers of two; heights are trimmed to the used area | Simple shelf packing per spec §5. WebGL2 / Pixi v8 handle non-power-of-two textures | 150–500 pieces from a 2048 px image fit in one atlas of about 3000×2800 |
| 17 | 2026-11-20 | A new worker is created for each bake and terminated afterwards. The worker gets a copy of the source bitmap (transferred). If the worker path fails for any reason, baking retries on the main thread in batches of 10 with `setTimeout(0)` yields. Worker support = `Worker` + `OffscreenCanvas` with a 2D context | Simplest lifecycle with no idle worker holding memory (NFR-6) | Worker start-up adds roughly 100 ms. The caller owns the atlas bitmaps and frees them with `disposeBakeResult` |
| 18 | 2026-11-20 | Import (spec §2): the 400 px minimum is checked on the decoded, oriented original before downscaling. An empty file counts as unsupported. Import runs on the main thread. Error messages are plain strings in `IMAGE_IMPORT_MESSAGES` until `t()` arrives in M5 | The spec doesn't say where import runs or whether the minimum applies before or after downscaling | Decoding a 12 MP JPEG takes ~400 ms on desktop (`createImageBitmap` is async, but the downscale draw and encode are on the main thread). Revisit if it causes visible jank on phones |

| 22 | 2026-11-20 | Model API: an immutable `BoardState` (`groups: Map<id, Group>`, a `pieceGroup` index, `maxZ`). The caller moves a group with `moveGroup` and then calls `drop(state, id)`. `drop` returns `{ state, groupId, absorbed, snapped, completed }`. Merge ranking (spec §6.1 step 3): most pieces wins; on a tie the already-placed group beats the dropped one (the dropped piece snaps to what's on the table), then the lower id. The merged group keeps the winner's id, position and rotation, and the highest `z` of the merged groups. Initial group ids equal piece ids | The spec defines the rule but not tie-breaking or ids | Group ids stay unique and stable, so the renderer can keep one container per surviving id and destroy the `absorbed` ones. Updates share unchanged groups (O(groups) pointer copy per drop) |
| 23 | 2026-11-20 | Not built in M3, because they are P1: board snap and locking (spec §6.1 step 5, the locked-group rule in step 3), rotating groups (§6.2), random rotations in scatter, and the edges-only candidate filter (§6.7). `locked` is always `false`. The fit check does compare `rot`, and `createInitialState` takes optional rotations, so the "no snap across rotations" rule is tested now | AGENTS.md rule 1 | Rotation mode (M7.1) and board snapping (M7.2) extend `drop` |
| 24 | 2026-11-20 | Scatter (spec §6.6): slots are square cells of `1.35·max(pw, ph)` in rings around the board. The first ring sits a gap of `piecePad` away from the board, so even tabs never cover it. Top/bottom bands span the full width including corners; side bands span the board height; cells are stretched evenly to tile each band. Rings start at `floor(0.6·max(w, h) / slot)` (at least 1) and grow until there are enough slots. Portrait: picks alternate 2 above/below : 1 side (shuffled per band), landscape 1 : 1. Each piece cell is jittered uniformly inside its slot. The random stream uses `seed XOR 0x5ca77e12`, independent of the shape stream | The spec leaves the slot layout and the weighting method open. Using integer interleaving avoids `Math.pow`/`Math.log`, whose results can differ between engines | Pieces never overlap each other or the board (tested for 12–500 pieces). `scatter` also returns the scatter `area` for camera zoom-to-fit (M4) |
| 25 | 2026-11-20 | Progress: `progressFraction` is spec §7's `(pieces − groups) / (pieces − 1)`, stored as `PuzzleMeta.progress`. The "23 / 48" top-bar count (spec §1.3) is `connectedPieces`: pieces in groups of 2 or more | The spec doesn't define the numerator of "connected pieces / total" | The two numbers differ mid-game (e.g. one merge = 2 connected, but 1/47 progress). Both reach the maximum at completion |
